Layout — one design TUI-L1

Every application uses one universal layout (operator decision 2026-07-23), defined in docs/tui/LAYOUT.md and rendered at four sizes in the layout artifact: app bar with the navigation path, content-sized nav, middle and detail/preview splitting the rest equally with contextual titles, help bar with navigation commands only. Narrow real estate stacks right items below left items; when stacking is impossible the panel's view becomes a modal. There is no per-screen layout choice. The floor is 80×24 (TUI-L2); multi-mode apps keep one frame (TUI-L3).

TUI-P1 Spatial consistency is the foundation

Panels don't move. Tabs stay in order. The user builds a mental map in the first minute and navigates by location memory after that. Every shuffle resets their spatial model to zero.

Panels TUI-PN

What lives inside a panel. This is the next design phase; nothing below is normative yet. PANELS.md is the editable decision worksheet for panel-internal geometry foundations. Its proposals have no TUI-PN rule IDs. Do not infer rules from illustrative Mike mockups or promote a proposal before it is decided.

Palette TUI-C4a

Colors are defined by function, not appearance (TUI-C4): widget code references slots, never values. Every value here is a published SilkCircuit Neon token (lua/silkcircuit/variants.lua) — the role text names the exact token. The Neon backgrounds are purple-tinted (#0a0812 → #12101a → #1a162a), primary text is warm white #f8f8f2, secondary text is lavender, muted text is blue-violet — neutral greys here would reproduce a generic dark theme and are Wrong. Each slot carries its nearest xterm-256 fallback (TUI-C2).

TUI-P4 Semantic color

Green = success, red = danger, yellow = caution. Color reinforces hierarchy already built by layout, typography, symbols. If stripping all color makes the app unusable, the design is broken.

TUI-P7 Design in layers

Monochrome: usable? → 16 ANSI: hierarchy readable? → truecolor: beautiful? Each tier independently usable. Works over a monochrome SSH session, stunning in Ghostty. A discipline, not a tradeoff.

State machines get a visual language (TUI-C6)

Each state maps to a color and a label and a style — consistently, everywhere it appears. The screen looks different when things are on fire.

hot — needs attention now
waiting — blocked on something
ready — good to go
dormant — stale
pending — awaiting action

Glyph vocabulary TUI-G1–G5

A documented vocabulary: every glyph a screen uses is listed with exactly one meaning, and one meaning never has two glyphs — consistency comes from the table, and additions extend it deliberately. Glyphs stay within the unambiguous-width set (double-width and ZWJ sequences break cell alignment — an engineering constraint, not taste). Sub-cell precision (fractional blocks, braille + halfblock charts) is for data display only, never decoration (TUI-G2). Border weight signals hierarchy — never uniform default borders everywhere (TUI-G3). Inspection content is never truncated: scroll or wrap, scroll, or paginate (TUI-G4). And the geometry is the cell grid's: square corners everywhere the design language appears — no pills, no rounded chrome, no desktop window dressing, on this page included (TUI-G5).

Navigation and help TUI-K · TUI-P2/P3/P6

Vim keys are the terminal lingua franca — six keystrokes handle 80% of navigation. Four layers, each invisible until the user reaches for it: progressive disclosure applied to the keyboard.

layerkeysdiscoverability
L0 universal↑↓←→ Enter Esc qhelp bar — anyone can use this
L1 vim navigationjkhl / ? : gGhelp bar — terminal natives expect this
L2 actionssingle mnemonics: d delete · s stage · r refresh? help overlay; same action = same key on every screen
L3 powercomposed commands · macros · configurationdocumentation only — the ceiling for experts

The help bar (TUI-P3: 3–5 keys, never a wall)

 j/k navigate  ·  Enter open  ·  / search  ·  ? help  ·  q quit

TUI-P2 Keyboard-first, mouse-optional

Every feature reachable without a mouse; mouse support not an afterthought. Power users are keyboard people, beginners will click. Support both; optimize for keys.

TUI-P3 Progressive disclosure, three tiers

Help bar with the 3–5 most important keys (always visible) → ? overlay with the full reference (on demand) → complete docs. Nobody reads a manual to get started.

TUI-P6 Contextual intelligence

Keybindings change as focus moves. The help bar shows only the commands available right now, and ? matches it. The UI earns trust by being accurate about what's possible.

Best practices for good UI TUI-P5 · TUI-A · TUI-B · TUI-V

The practices that keep the TUI honest: never block, push don't poll, show processing while it happens, and keep the UI drivable and verifiable by AI agents.

TUI-P5 Async everything

Never freeze the UI. File I/O, network, DB — background tasks with progress indicators. Esc always returns a responsive interface. A TUI that hangs is a TUI that gets killed.

TUI-B1 AI-friendly UI

AI agents build, drive, and verify this TUI, and they are blind by default. Every state change flows through the event system (TUI-A2) so an agent can reason about it; every feature is reachable by keys (TUI-P2); the CLI face exposes the same data scriptably (TUI-A3); the rendered screen is verifiable in a real terminal (TUI-V1). design → build → run → see → fix → repeat.

Architecture with design consequences (TUI-A)

TUI-A1 Never poll; push

The UI is told when something changes (watch/broadcast channels) — it never asks “has anything changed?” on a timer. The responsiveness difference is visceral.

TUI-A2 events → state → render

Pure reducers: (state, event) → (new state, side effects), no I/O inside. Application events and agent output flow through the same event system as keystrokes. Testable, debuggable, auditable.

TUI-A3 Know when not to be a TUI

One core, two faces: scriptable CLI (plain/JSON, pipe-composable, zero decoration) and the interactive TUI. When stdout is a pipe: no color and no boxes.

Verification (TUI-V)

An agent building a TUI is blind by default — stdout text can't verify that borders line up or that j/k navigates. Every TUI change is verified by running the app in a real terminal and reading the rendered screen (pty harness, snapshot tests). A passing unit test is not a substitute for seeing the screen. Verify per layer: snapshot monochrome, 16-color, truecolor × 80×24 and the wider reference size.

Screen-spec checklist

Every screen spec — and every review of one — checks:

  • Uses the universal layout — app bar path, nav/middle/detail-preview with contextual titles, navigation-only help bar in the final row TUI-L1 · LAYOUT.md
  • Exact 80×24 mockup + wider reference; narrow-width behavior stated TUI-L2
  • Keymap listed by layer L0–L3; help bar shows 3–5 keys; ? overlay defined TUI-K2 · TUI-P3
  • All colors as semantic slots with 256-color fallback; no raw values TUI-C2 · TUI-C4
  • Usable-when-stripped: hierarchy holds in monochrome TUI-P4 · TUI-P7
  • Every glyph used is in the documented vocabulary TUI-G1
  • Loading/empty/error/populated states specified; nothing blocks the event loop TUI-P5
  • Focus-dependent keybindings enumerated; help bar matches the current navigation context and carries no status TUI-P6
  • No truncation of inspection content — wrap/scroll/paginate TUI-G4
